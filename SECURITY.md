# Security, Privacy & Compliance Architecture

This document details the security model, biometric data protection mechanisms, anti-spoofing defense controls, and compliance features implemented in the **Smart Attendance Management System**.

---

## 1. Biometric Data Protection & Privacy

Biometric facial recognition data is classified as sensitive personal information. The system enforces strict architectural guardrails to protect biometric privacy:

### 1.1 Vector Shielding & Schema Isolation
- **Raw Biometric Vector Shielding**: The 128-dimensional floating-point embeddings generated by the SFace neural network are strictly stored in internal database tables and the in-memory SIMD cache.
- **Zero Exposure in Public APIs**: Pydantic response models (`StudentResponse`, `StudentDetailResponse`, `AttendanceRecordResponse`) explicitly exclude embedding vectors. Client applications only receive high-level status indicators (`face_registered: true`, `confidence_score: 0.884`).
- **Cryptographic Hashing & Salting**: Passwords are never stored in plaintext. They are protected using **Argon2id** (memory-hard, GPU-resistant) with unique salts per user.

### 1.2 Zero Mock / Zero Synthetic Policy
- The production facial recognition pipeline strictly relies on true deep learning inferences (YuNet + SFace).
- No mock endpoints or bypass flags exist in the production attendance marking pipeline.

### 1.3 Right to Erasure (Biometric Reset)
- Administrators can immediately purge all biometric embeddings for any student via `DELETE /api/v1/students/{id}/face-embeddings`.
- Deleting biometric data immediately triggers an eviction event in the SIMD `EmbeddingCacheManager`, ensuring vectors are wiped from both disk and RAM.

## 2. Anti-Spoofing & Replay Attack Defense

The platform utilizes a multi-layer defense strategy against presentation attacks:

| Attack Vector | Vulnerability Description | System Defense Mechanism |
| :--- | :--- | :--- |
| **Printed Photograph** | Attacker presents a high-resolution 2D paper photo to the webcam. | **Active Challenge-Response**: Demands dynamic physical actions (head yaw turn or eye blink). A static photo cannot execute state transitions. |
| **Video Replay (Tablet/Phone)** | Attacker plays a pre-recorded video of the student blinking or smiling. | **Randomized Action Order & 25s TTL**: The required sequence (e.g. `TURN_LEFT` followed by `SMILE`) is randomized at runtime and expires in 25 seconds. |
| **Token Interception / Replay** | Attacker intercepts a valid completion token and attempts to mark multiple times. | **Single-Use Cryptographic Receipts**: Receipt tokens self-destruct upon the first database write. Replay attempts are rejected with `HTTP 400 Bad Request`. |
| **Oversized Media DoS** | Attacker floods the API with 50MB raw video payloads to exhaust server memory. | **PayloadLimitMiddleware**: Rejects payloads exceeding 15MB with `HTTP 413 Payload Too Large`. |

## 3. Sliding-Window Rate Limiting

To prevent credential brute-force attacks and denial-of-service attempts against computer vision inference endpoints, an in-memory **Sliding-Window Rate Limiter** is enforced per client IP:

```
                  ┌─────────────────────────────────────┐
                  │ Request Arrival (Client IP Address) │
                  └──────────────────┬──────────────────┘
                                     │
                  ┌──────────────────▼──────────────────┐
                  │ Clean Timestamps Older than 60 Sec  │
                  └──────────────────┬──────────────────┘
                                     │
                          Is Window Count < Limit?
                         /                        \
                   YES  /                          \  NO
                       ▼                            ▼
         ┌───────────────────────────┐    ┌───────────────────────────┐
         │ Append Current Timestamp  │    │ HTTP 429 Too Many Req     │
         │ Allow Request to Proceed  │    │ Header: Retry-After = 60  │
         └───────────────────────────┘    └───────────────────────────┘
```

### Rate Limits by Endpoint:
- **Authentication (`/auth/login`)**: 10 requests / minute
- **Biometric Enrollment (`/students/{id}/enroll-faces`)**: 20 requests / minute
- **Liveness Challenge (`/attendance/liveness/*`)**: 60 requests / minute
- **Attendance Marking (`/attendance/mark`)**: 60 requests / minute

## 4. HTTP Security Headers

Every HTTP response emitted by the FastAPI backend includes defensive security headers configured via `SecurityHeadersMiddleware`:

```http
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
X-XSS-Protection: 1; mode=block
Permissions-Policy: camera=(self)
Referrer-Policy: strict-origin-when-cross-origin
```
- **`Permissions-Policy: camera=(self)`**: Restricts webcam access strictly to the application origin, preventing iframe injection attacks from hijacking camera streams.
- **`X-Frame-Options: DENY`**: Protects the live attendance kiosk from clickjacking.

## 5. Audit Trail & Forensic Logging

Every sensitive administrative and attendance operation creates an immutable record in the `audit_logs` table:

```json
{
  "id": 84,
  "user_id": 2,
  "action": "ATTENDANCE_MANUAL_OVERRIDE",
  "entity_type": "AttendanceRecord",
  "entity_id": "195",
  "ip_address": "192.168.1.45",
  "details_json": "{\"session_id\": 12, \"student_id\": 42, \"remarks\": \"Medical certificate presented\"}",
  "created_at": "2026-09-11T10:14:02Z"
}
```

### Tracked Audit Events:
- `LOGIN_SUCCESS` / `LOGIN_FAILURE` / `LOGOUT`
- `STUDENT_CREATED` / `STUDENT_UPDATED` / `STUDENT_DELETED`
- `FACE_ENROLLED` / `FACE_DELETED`
- `SESSION_CREATED` / `SESSION_STOPPED`
- `ATTENDANCE_MANUAL_OVERRIDE`
